# 架构与路线

Pai 将论文转成适合 AI 消费、能回到原文核对的数据。优先优化原生电子论文，扫描识字通过可选组件补充。质量、速度、峰值内存需在相同语料与配置下分别测量。

```text
CLI / Python API
        ↓
parser：文档遍历、逐页路由、异常隔离、状态汇总
        ↓
backends/pymupdf：原生行、位图区域、表格、受限渲染
        ↓
ocr：按需识字，可注入 OcrProvider
        ↓
layout：位置去重、阅读顺序、段落与页眉页脚
        ↓
paper：章节路径、图表说明、参考文献角色
        ↓
统一 document dict → export / chunking
```

`config.Options` 是不可变且经过验证的配置。公开入口在 `api.py`；导入包不会加载 PDF 后端、推理框架或模型。

`parser.py` 通过后端函数获取原生内容，但目前仍管理 PyMuPDF 文档/页面对象和生命周期。因此后端已在文件层面分离，尚不是可任意替换的完整插件协议。OCR 已有显式协议，测试可注入离线识别器。

JSON 是统一中间数据，Markdown、报告和分块均从同一对象生成。原始行与坐标保留，结构推断不修改源 PDF。

## 资源策略

- 无 OCR 需求时不导入 RapidOCR、ONNX Runtime、NumPy 等模块。
- 不加载通用版面、表格或生成模型；后续可按需增加增强器。
- 每次渲染默认最多约 600 万像素；像素取整可能带来小量超出。文档结果仍在内存累积。
- OCR 在一次转换内复用，默认 2 个线程。不启用隐式多进程。
- 来源冲突时保留证据并标记；整页 OCR 替代原生块时另存 `raw_native_lines`。

## 后续优先级

1. 建立固定真实论文评测集：单栏、双栏、中文、公式、无框表格、扫描版；固定真值和版本。
2. 根据错误分布改善跨栏顺序、脚注与断行；避免仅在合成样例上调规则。
3. 为低质量区域接入可选版面、表格、公式增强器，分别记录耗时、来源和质量，保持基础安装轻量。
4. 抽象完整 PDF 文档/页面协议，评估替代后端的质量、性能和许可；增加可选流式输出。

目前没有自动 fallback 到 Docling，也没有默认模型增强。先建立质量基线，再决定引入哪些模型。
